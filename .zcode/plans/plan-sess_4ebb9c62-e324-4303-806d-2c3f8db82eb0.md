# Migrate dbt project from MySQL → DuckDB

**Context found:** Current setup is dbt-core 1.7.20 + dbt-mysql 1.7.0 (`.venv-dbt`, Python 3.12), profile `fmcg_sales` targeting MySQL `sales_of_fmcg_stores`. Raw data = 7 CSVs in `Dataset/` (sales.csv = 517 MB, 6,758,125 rows) loaded via `LOAD DATA INFILE` scripts. 25 models (7 staging views, 3 intermediate views, 15 marts). The pain point is confirmed: `int_sales_metrics` took **9 min 18 s** on MySQL. MySQL-specific syntax is minimal: `date_format()` in 2 files, index hooks in 1 file, plus `macros/mysql_indexes.sql` — everything else (`concat()`, `year()`, `month()`, joins) is DuckDB-compatible as-is.

**Note:** the existing `.venv` already contains duckdb 1.5.5 + dbt-duckdb 1.11.0 packages, but it runs Python **3.14.0a7 (an alpha)** and has no `dbt.exe` entrypoint — do not build on it. We'll make a clean venv on Python 3.12 instead.

---

## Step 0 — Safety net (5 min)
1. Commit current uncommitted work on the `dbt` branch, then tag it: `git tag mysql-baseline` — everything is revertable.
2. Leave `.venv-dbt`, MySQL server, and `profiles.yml` MySQL output **untouched** throughout; MySQL stays the dashboards' source.

## Step 1 — New venv (10 min)
```bash
py -3.12 -m venv .venv-duckdb
.venv-duckdb/Scripts/pip install dbt-duckdb
.venv-duckdb/Scripts/dbt --version   # verify
```
This installs dbt-core 1.12.x + duckdb together. (Old `requirements.txt` pins dbt 1.7/dbt-mysql; we update it in Step 7.)

## Step 2 — Profile (5 min)
In `profiles.yml`, add a new output next to the existing `dev` (keep `dev` for rollback):
```yaml
fmcg_sales:
  target: duckdb_dev
  outputs:
    duckdb_dev:
      type: duckdb
      path: fmcg.duckdb        # project root
      schema: main
      threads: 8
    dev:                        # existing MySQL output, unchanged
      ...
```
Flip `target:` to `duckdb_dev` only at Step 7.

## Step 3 — One-time raw load script (15 min)
Create `scripts/load_raw.py` using the venv's `duckdb` package. Connect to `fmcg.duckdb`, `CREATE SCHEMA IF NOT EXISTS raw`, then for each of the 7 CSVs: `CREATE OR REPLACE TABLE raw.<name> AS SELECT * FROM read_csv('Dataset/<name>.csv', header = true, auto_detect = true, ...)` with explicit types where it matters — `sales.SalesDate` as TIMESTAMP, `Discount`/`TotalPrice`/`Price` as DOUBLE, big IDs (CustomerID: 98,759 rows) as BIGINT, `TransactionNumber` as VARCHAR. Use `normalize_names = false` to keep original column casing (models reference `SalesID`, `SalesDate`, etc.). Print row counts per table. Idempotent — safe to re-run. Run it: ~6.76M rows loads in seconds. This replaces `Dataset/upload_*.sql` (kept on disk for reference).

## Step 4 — Point sources at DuckDB (5 min)
`models/sources.yml`: change `schema: "{{ target.schema }}"` → `schema: raw`. All 7 source tables and their tests stay unchanged.

## Step 5 — Model syntax fixes (10 min)
1. `models/intermediate/int_sales_metrics.sql:21` — `date_format(s.SalesDate, '%Y-%m')` → `strftime(s.SalesDate, '%Y-%m')` (identical output format).
2. `models/intermediate/int_sales_enriched.sql:6` — same change.
3. `models/intermediate/int_sales_metrics.sql` — remove the entire `pre_hook`/`post_hook` index config (lines 4–11): DuckDB is columnar, these MySQL indexes are pointless and the macros become no-ops.
4. Delete `macros/mysql_indexes.sql`.
5. `concat()` in marts is DuckDB-native — no changes needed elsewhere.

## Step 6 — Build + parity validation (20 min)
```bash
.venv-duckdb/Scripts/dbt debug --target duckdb_dev
.venv-duckdb/Scripts/dbt build --target duckdb_dev
```
`dbt build` runs all models + the source/mart tests. Validate parity against MySQL (query both, expect exact row counts and totals since the SQL logic is unchanged):
- row counts: `monthly_revenue`, `monthly_category_revenue_summary`, `salesperson_performance_summary`, `customer_behavior_summary`, `geographic_revenue_with_region`
- total revenue sum from `monthly_revenue` on both engines
Capture before/after timings — expect `int_sales_metrics` 9m18s → seconds, full build in well under a minute.

## Step 7 — Cutover + cleanup (5 min)
1. `profiles.yml`: default `target: duckdb_dev` (already written in Step 2, just confirm).
2. `requirements.txt`: replace `dbt-mysql==1.7.*` → `dbt-duckdb`.
3. `.gitignore`: add `*.duckdb` and `*.duckdb.wal`.
4. README: document the new venv, `load_raw.py`, run commands, and the DuckDB architecture.
5. Commit on the `dbt` branch.

## Step 8 — Power BI (deferred, per your choice)
Dashboards keep refreshing from MySQL for now. I'll add a short "Power BI migration (later)" section to the README documenting the path: install the DuckDB ODBC driver (github.com/duckdb/duckdb-odbc, Windows x64), create a DSN pointing at `fmcg.duckdb`, re-point each PBIX's source in Power Query — mart table names are identical, so remapping is mechanical. Note the DuckDB single-writer file lock: close/refresh PBI outside `dbt build` windows, or switch to the Parquet-export option if conflicts appear.

---

**Risks / notes**
- dbt 1.12 may emit deprecation warnings for the `tests:` key in `schema.yml` — harmless; optionally rename to `data_tests`.
- DuckDB allows one writer process at a time — don't run concurrent `dbt build`s.
- Rollback at any point: `git checkout mysql-baseline` + use `.venv-dbt` + MySQL, which never gets modified.
